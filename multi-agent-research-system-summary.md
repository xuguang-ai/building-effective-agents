## One-sentence takeaway

Anthropic's Research feature is an orchestrator-worker system in which a lead agent plans, spawns parallel search subagents with their own context windows and hands the findings to a citation agent; it beat a single agent by 90.2% on an internal eval mainly because it spends more tokens (token usage alone explains 80% of BrowseComp variance) at roughly 15× the token cost of a chat, and taking it to production required detailed delegation prompts, effort-scaling rules, good tool descriptions, small-sample evals with an LLM judge, full tracing, resumable state and rainbow deployments.

## 1. Benefits of a multi-agent system

The post opens with context: Claude now has Research capabilities that search across the web, Google Workspace and any integrations to accomplish complex tasks. A multi-agent system is defined as "multiple agents (LLMs autonomously using tools in a loop) working together"; in Research, one agent plans the research process from the user's query and then uses tools to create parallel agents that search simultaneously. Multiple agents introduce new challenges in coordination, evaluation and reliability, and the lessons cover system architecture, tool design and prompt engineering.

- **Research is open-ended** and path-dependent: the required steps cannot be predicted or hardcoded in advance; people continuously update their approach based on discoveries and follow leads that emerge during the investigation. This suits agents: the model must operate autonomously for many turns and decide which directions to pursue from intermediate findings. "A linear, one-shot pipeline cannot handle these tasks."
- **Search is compression**, distilling insights from a vast corpus. Subagents compress by working in parallel with their own context windows, exploring different aspects at the same time and condensing the most important tokens for the lead research agent. Each subagent also provides separation of concerns (distinct tools, prompts and exploration trajectories), which reduces path dependency and enables thorough, independent investigations.
- **The scaling argument**: once intelligence reaches a threshold, multi-agent systems become a vital way to scale performance. Analogy: individual humans have become more intelligent over the last 100,000 years, but human societies became exponentially more capable in the information age through collective intelligence and the ability to coordinate. Even generally intelligent agents face limits as individuals; groups can accomplish far more.
- **Headline result**: internal evaluations show multi-agent research systems excel especially at breadth-first queries that pursue multiple independent directions at once. A system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on the internal research eval. Example: asked to identify all board members of the companies in the Information Technology S&P 500, the multi-agent system decomposed the task into subagent tasks and found the correct answers, while the single agent failed with slow, sequential searches.
- **Why it works: tokens**. Multi-agent systems work mainly because they help spend enough tokens to solve the problem. In Anthropic's analysis of the BrowseComp evaluation (which tests the ability of browsing agents to locate hard-to-find information), three factors explained 95% of the performance variance; token usage by itself explains 80%, with the number of tool calls and the model choice as the two other factors. This validates distributing work across agents with separate context windows to add capacity for parallel reasoning. Newer models are large efficiency multipliers on token use: upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7.
- **The downside: cost and fit**. In Anthropic's data, agents typically use about 4× more tokens than chat interactions and multi-agent systems about 15× more than chats, so the task must be valuable enough to pay for the extra performance. Domains that require all agents to share the same context, or that involve many dependencies between agents, are not a good fit today: most coding tasks have fewer truly parallelizable parts than research, and LLM agents are "not yet great at coordinating and delegating to other agents in real time". The sweet spot is valuable tasks with heavy parallelization, information that exceeds a single context window, and many complex tools.

## 2. Architecture overview for Research

- **Orchestrator-worker pattern**: a lead agent coordinates the process and delegates to specialized subagents that operate in parallel. When a query arrives, the lead agent analyzes it, develops a strategy and spawns subagents to explore different aspects simultaneously. The subagents act as intelligent filters, iteratively using search tools (in the example, on AI agent companies in 2025) and returning a list to the lead agent, which compiles the final answer.
- **Figure 1, "High-level Architecture of Advanced Research"**: on the left, a Claude.ai chat panel with the sample request "what are all the companies in the united states working on AI agents in 2025? make a list of at least 100. for each company, include the name, website, product, description of what they do, type of agents they build, and their vertical/industry." A "User request" arrow enters the multi-agent research system and a "Final report" arrow returns. On the right, the "Lead agent (orchestrator)" box lists its tools as "search tools + MCP tools + memory + run_subagent + complete_task"; it has a two-way link to a "Memory" box, an arrow to a "Citations subagent", and two-way arrows to three "Search subagent" boxes, each drawn with a loop arrow for its own iterative searching.
- **Versus RAG**: traditional Retrieval Augmented Generation uses static retrieval, fetching the chunks most similar to the query and generating from them. The Research architecture instead runs a multi-step search that dynamically finds relevant information, adapts to new findings and analyzes results to formulate high-quality answers.
- **Figure 2, "Multi-agent System Process Diagram"**, a sequence diagram with lanes User, System, LeadResearcher, Subagent1, Subagent2, Memory and CitationAgent. The user sends a query; the System creates the LeadResearcher. Inside an "Iterative Research Process" box the LeadResearcher does "think (plan approach)", then "save plan" to Memory and "retrieve context" from it, then "create subagent for aspect A" and "create subagent for aspect B". Each subagent runs "web_search" and "think (evaluate)" loops and reports back with "complete_task". The LeadResearcher does "think (synthesize results)" and reaches a "More research needed?" decision with two exits, "Exit loop" and "Continue loop". After the loop it sends "complete_task (research result)" to the System; the CitationAgent processes "documents + research report to identify locations for citations" and returns the report with citations inserted; the System persists the results and returns "research results with citations" to the user.
- **Details from the caption**: the plan is saved to Memory because if the context window exceeds 200,000 tokens it will be truncated and the plan must be retained; two subagents are drawn but the number is arbitrary; each subagent independently performs web searches and evaluates tool results with interleaved thinking; the lead synthesizes and decides whether more research is needed, creating additional subagents or refining its strategy; the CitationAgent ensures all claims are properly attributed to their sources.

## 3. Prompt engineering and evaluations for research agents

Coordination complexity grows rapidly in multi-agent systems. Early agents spawned 50 subagents for simple queries, scoured the web endlessly for nonexistent sources and distracted each other with excessive updates. Since each agent is steered by a prompt, prompt engineering was the primary lever. The eight principles:

1. **Think like your agents.** To iterate on prompts you must understand their effects, so Anthropic built simulations in its Console with the exact prompts and tools from the system and watched agents work step by step. This immediately revealed failure modes: continuing when results were already sufficient, overly verbose search queries, and wrong tool selection. Effective prompting relies on an accurate mental model of the agent, which makes the most impactful changes obvious.
2. **Teach the orchestrator how to delegate.** The lead agent decomposes queries into subtasks and describes them to subagents; each subagent needs an objective, an output format, guidance on tools and sources, and clear task boundaries. Without detailed descriptions agents duplicate work, leave gaps or fail to find information. Short instructions such as 'research the semiconductor shortage' were vague enough that subagents misinterpreted the task or ran the same searches: one subagent explored the 2021 automotive chip crisis while 2 others duplicated work on current 2025 supply chains.
3. **Scale effort to query complexity.** Agents struggle to judge appropriate effort, so scaling rules are embedded in the prompts: simple fact-finding needs just 1 agent with 3-10 tool calls; direct comparisons might need 2-4 subagents with 10-15 calls each; complex research might use more than 10 subagents with clearly divided responsibilities. This prevents overinvestment in simple queries, a common failure in early versions.
4. **Tool design and selection** are critical. Agent-tool interfaces are as critical as human-computer interfaces; an agent searching the web for context that only exists in Slack "is doomed from the start". MCP servers compound the problem because agents meet unseen tools with descriptions of wildly varying quality. Heuristics given to the agents: examine all available tools first, match tool usage to user intent, search the web for broad external exploration, prefer specialized tools over generic ones. Bad descriptions send agents down completely wrong paths, so each tool needs a distinct purpose and a clear description.
5. **Let agents improve themselves.** Claude 4 models can be excellent prompt engineers: given a prompt and a failure mode, they diagnose why the agent fails and suggest improvements. A tool-testing agent, given a flawed MCP tool, tries to use it and rewrites the tool description to avoid failures; testing the tool dozens of times surfaced key nuances and bugs, and the new descriptions produced a 40% decrease in task completion time for future agents because they avoided most mistakes.
6. **Start wide, then narrow down.** Search strategy should mirror expert human research: explore the landscape before drilling into specifics. Agents default to overly long, specific queries that return few results; the prompts counteract this by starting with short, broad queries, evaluating what is available, then progressively narrowing focus.
7. **Guide the thinking process.** Extended thinking mode, which has Claude output additional tokens in a visible thinking process, serves as a controllable scratchpad. The lead agent uses it to plan its approach, assess which tools fit, determine query complexity and subagent count, and define each subagent's role; testing showed improved instruction-following, reasoning and efficiency. Subagents also plan, then use interleaved thinking after tool results to evaluate quality, identify gaps and refine the next query.
8. **Parallel tool calling** transforms speed and performance. Early agents executed sequential searches, which was painfully slow. Two kinds of parallelization were introduced: (1) the lead agent spins up 3-5 subagents in parallel rather than serially; (2) subagents use 3+ tools in parallel. This cut research time by up to 90% for complex queries, doing in minutes what took hours while covering more information than other systems.

The strategy instils good heuristics rather than rigid rules. Anthropic studied how skilled humans research and encoded those strategies: decomposing difficult questions into smaller tasks, carefully evaluating source quality, adjusting the search approach on new information, and recognizing when to go deep (one topic in detail) versus broad (many topics in parallel). Explicit guardrails stop agents spiralling out of control, and the team kept a fast iteration loop with observability and test cases.

## 4. Effective evaluation of agents

- **Why agent evals differ**: traditional evaluations assume the same steps every time (given input X, follow path Y, produce output Z), but agents may take completely different valid paths, searching three sources or ten, or using different tools for the same answer. Since the right steps are not known in advance, you usually cannot check whether agents followed prescribed "correct" steps; flexible methods must judge whether the right outcome was reached while the process stayed reasonable.
- **Start evaluating immediately** with small samples. Early changes have dramatic effects because of abundant low-hanging fruit: a prompt tweak might boost success rates from 30% to 80%, which a few test cases can detect. Anthropic started with about 20 queries representing real usage patterns. Teams often delay evals believing only hundreds of test cases are useful; the advice is to start small right away.
- **LLM-as-judge evaluation** scales when done well. Research outputs are free-form text with rarely a single correct answer, so an LLM grades each output against a rubric: factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness (are all requested aspects covered?), source quality (primary sources over lower-quality secondary ones?) and tool efficiency (the right tools, a reasonable number of times?). Multiple judges per component were tried, but a single LLM call with a single prompt outputting scores from 0.0-1.0 plus a pass-fail grade was the most consistent and best aligned with human judgements. It worked especially well when test cases had a clear answer, for example "did it accurately list the pharma companies with the top 3 largest R&D budgets?", and it scaled to hundreds of outputs.
- **Human evaluation** catches what automation misses: hallucinated answers on unusual queries, system failures and subtle source-selection biases. Human testers noticed that early agents consistently chose SEO-optimized content farms over authoritative but less highly ranked sources such as academic PDFs or personal blogs; adding source-quality heuristics to the prompts fixed it. Manual testing remains essential even with automated evals.
- **Emergent behaviors**: small changes to the lead agent can unpredictably change how subagents behave, so success requires understanding interaction patterns, not just individual agents. The best prompts are "frameworks for collaboration" that define the division of labor, problem-solving approaches and effort budgets, relying on careful prompting and tool design, solid heuristics, observability and tight feedback loops. The system's example prompts are open-sourced in the Cookbook.

## 5. Production reliability and engineering challenges

In traditional software a bug breaks a feature, degrades performance or causes an outage; in agentic systems minor changes cascade into large behavioral changes, which makes it remarkably hard to write code for complex agents that maintain state in a long-running process.

- **Agents are stateful** and errors compound. Agents run for long periods with state across many tool calls, so code must execute durably and handle errors along the way; without mitigations, minor failures are catastrophic. Restarting from the beginning is expensive and frustrating, so the systems resume from where the agent was when the error occurred. The model's own intelligence helps: telling the agent that a tool is failing and letting it adapt "works surprisingly well". This adaptability is combined with deterministic safeguards such as retry logic and regular checkpoints.
- **Debugging** benefits from new approaches. Agents are non-deterministic between runs even with identical prompts. Users reported agents "not finding obvious information", and the team could not see why (bad search queries? poor sources? tool failures?). Full production tracing let them diagnose failures and fix issues systematically. Beyond standard observability they monitor agent decision patterns and interaction structures, without monitoring the contents of individual conversations, to maintain user privacy.
- **Deployment** needs careful coordination. Agent systems are highly stateful webs of prompts, tools and execution logic that run almost continuously, so at deploy time agents may be anywhere in their process and cannot all be updated at once. Anthropic uses rainbow deployments: traffic shifts gradually from old to new versions while both keep running, so running agents are not disrupted.
- **Synchronous execution** creates bottlenecks. Currently lead agents execute subagents synchronously, waiting for each set to complete. This simplifies coordination but the lead cannot steer subagents, subagents cannot coordinate with each other, and the whole system can block while one subagent finishes searching. Asynchronous execution would let agents work concurrently and create new subagents when needed, at the cost of harder result coordination, state consistency and error propagation; the team expects the gains to justify the complexity as models handle longer, more complex research tasks.

## 6. Conclusion

- **The last mile**: "when building AI agents, the last mile often becomes most of the journey." Codebases that work on developer machines need significant engineering to become reliable production systems; because errors compound, issues that are minor in traditional software can derail agents entirely, and one failing step can send an agent down an entirely different trajectory. The gap between prototype and production is often wider than anticipated.
- **The payoff**: users said Claude helped them find business opportunities they had not considered, navigate complex healthcare options, resolve thorny technical bugs, and save up to days of work by uncovering research connections they would not have found alone. Reliable operation at scale needs careful engineering, comprehensive testing, detail-oriented prompt and tool design, robust operational practices, and tight collaboration between research, product and engineering teams who understand current agent capabilities.

## 7. Appendix: additional tips for multi-agent systems

- **End-state evaluation** of agents that mutate state over many turns. When each action changes the environment for later steps, traditional turn-by-turn evaluation struggles. Judge whether the agent reached the correct final state rather than whether it followed a specific process; this accepts alternative paths to the same goal. For complex workflows, break evaluation into discrete checkpoints where specific state changes should have occurred instead of validating every intermediate step.
- **Long-horizon conversation management.** Production conversations can span hundreds of turns, exceeding standard context windows. Agents summarize completed work phases and store essential information in external memory before moving on; when context limits approach they can spawn fresh subagents with clean contexts, keeping continuity through careful handoffs, and retrieve stored context such as the research plan instead of losing earlier work at the limit.
- **Subagent output to a filesystem** to minimize the 'game of telephone'. Subagent outputs can bypass the coordinator for certain results: specialized agents create artifacts that persist independently, store their work in external systems through tool calls and pass lightweight references back. This prevents information loss across multi-stage processing and cuts the token overhead of copying large outputs through conversation history; it suits structured outputs such as code, reports or data visualizations, where the subagent's specialized prompt produces better results than filtering through a general coordinator.
